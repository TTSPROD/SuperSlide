# SuperSlide

Локальный прототип генерации редактируемых презентаций PowerPoint в корпоративном оформлении. Вход — описание задачи и документы; результат — `.pptx`. Для генерации содержания используется внутренний API текстовой модели. Подготовленный JSON можно собрать в презентацию без обращения к модели.

Схема работы: **запрос, документы и описания локальных фотографий → JSON по строгой схеме → проверка → фирменные макеты → PPTX**. Модель выбирает разрешённый тип слайда, заполняет его содержание и при необходимости выбирает фотографию из каталога. Расположение объектов, шрифты и цвета определяет генератор.

## Статус прототипа

Версия **1.2 поддерживает 31 вариант оформления для 14 типов слайдов**. К 14 исходным композициям добавлены 17 вариантов: разные титульные слайды, разделители, цитаты, композиции с фотографиями, карточки KPI и финальные слайды. Тип содержания задаёт `layout_id`, а конкретную композицию — `variant_id`. Варианты опираются на предоставленные брендбук и корпоративную библиотеку; происхождение и адаптации описаны в [карте вариантов](docs/brand-variants.md).

В `examples/variants.json` представлены все варианты оформления на 31 слайде. Пример `examples/variety.json` версии 1.1 содержит 14 слайдов: по одному каждого типа с оформлением `default`. Старый `examples/presentation.json` версии 1.0 содержит шесть базовых типов. Оба примера остаются совместимыми: если `variant_id` отсутствует, выбирается `default`, и прежняя композиция сохраняется.

Проверено 16 ноября 2026 года: **90 автоматических тестов прошли**, аудит шаблона подтвердил весь набор из 31 оформления и сохранение прежних 14 композиций. Демонстрационная презентация `variants.pptx` из 31 слайда успешно открыта в **Microsoft PowerPoint 16.0** и экспортирована в PDF и PNG. Проверка высоты текстовых рамок не выявила переполнений; выполнен визуальный просмотр всех слайдов, включая кадрирование фотографий. В файле сохранены 10 фотографий, одна нативная таблица и одна нативная диаграмма.

Готовые результаты: [презентация на 31 слайде](output/variants.pptx), [PDF](output/variants-powerpoint/presentation.pdf), [обложки и разделители](output/variants-preview.png), [варианты содержательных слайдов](output/variants-content.png), [отчёт проверки PowerPoint](output/variants-powerpoint/powerpoint-report.json). Числа и содержание демонстрационные; фотографии взяты из предоставленного корпоративного шаблона. Прежняя [демонстрация 14 композиций](output/variety.pptx) и её [PDF](output/variety-powerpoint/presentation.pdf) также доступны.

Отдельно ранее проверена генерация через корпоративную модель **`glm-5.3` и LiteLLM**: для прежнего примера с шестью базовыми макетами валидный JSON получен с первой попытки, числа таблицы и диаграммы совпали с исходными данными. Сохранены [PPTX модели](output/glm-presentation.pptx), [JSON](output/glm-draft.json) и [источники](output/glm-sources.json). Этот прогон подтверждает подключение к API. Демонстрации `variety` и `variants` собраны из подготовленного JSON без вызова модели; контракт API и выбор вариантов проверены тестами с подменой ответов сервиса. Живая генерация новых вариантов через `glm-5.3` отдельно не проверялась.

Тексты, карточки, таблицы и диаграммы создаются нативными объектами PowerPoint. Фотографии вставляются обычными объектами изображения: их можно перемещать, заменять и кадрировать в PowerPoint. Слайд целиком не превращается в картинку; пиксели фотографий не становятся редактируемыми фигурами.

Генераторный шаблон — облегчённая версия, подготовленная программно на основе исходных материалов. Это **не утверждённый владельцем бренда корпоративный шаблон**. Оформление требует согласования, а новые презентации — проверки в целевой версии PowerPoint. В качестве разрешённого брендбуком запасного шрифта используется Arial; переход на Grtsk Peta требует согласованного набора шрифтов и проверки их доступности на компьютерах пользователей.

Рабочее подключение настроено в `config/llm.local.json`; адрес сервиса не включён в публичные примеры. Для повторного запуска нужно задать API-ключ через переменную окружения. Значения в `config/llm.example.json` служат примером. Проверка на демонстрационных документах подтверждает работу цепочки генерации, но новые материалы требуют проверки содержания и оформления.

## Установка на Windows

Нужен Python 3.11 или новее. Основные зависимости: `python-pptx`, Pydantic 2, `python-docx`, `pypdf`, Pillow; сборка проверена с `python-pptx` 1.0.2. Выполняйте команды из корня проекта в PowerShell.

При наличии готового Python с зависимостями можно сразу пользоваться `run.ps1`. Он поддерживает окружение `.venv`, явный путь к интерпретатору в `SUPERSLIDE_PYTHON` и уже установленный Python из среды Codex. Launcher не устанавливает Python или зависимости автоматически.

```powershell
.\run.ps1 inspect-template
.\run.ps1 build examples/variety.json --output output/variety.pptx
```

Для самостоятельной установки окружения:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e .
```

Если активация окружения недоступна, запускайте `.\.venv\Scripts\python.exe` напрямую. Команды `run.ps1` также можно выполнять как `python -m superslide ...` в установленном окружении.

## Проверка сборки без модели

В `examples/variants.json` подготовлен 31 слайд со всеми вариантами оформления; в `examples/variety.json` — 14 прежних композиций `default`. В обоих примерах используются локальные корпоративные фотографии, а числа и содержание демонстрационные. Обращение к API для этих команд не требуется.

```powershell
.\run.ps1 inspect-template
.\run.ps1 assets
.\run.ps1 validate examples/variants.json
.\run.ps1 build examples/variants.json --output output/variants.pptx --report output/variants.report.json
.\run.ps1 validate examples/variety.json
.\run.ps1 build examples/variety.json --output output/variety.pptx --report output/variety.report.json
```

Для проверки совместимости с версией 1.0 используйте прежний пример на шесть слайдов:

```powershell
.\run.ps1 validate examples/presentation.json
.\run.ps1 build examples/presentation.json --output output/demo.pptx --report output/demo.report.json
```

Откройте `output/variety.pptx` в используемой компанией версии PowerPoint. Проверьте переносы текста, шрифты, подписи, таблицу, диаграмму и кадрирование фотографий; попробуйте изменить текст, ячейки таблицы и данные диаграммы, заменить изображение. Уведомление PowerPoint о восстановлении содержимого считается ошибкой сборки.

Шаблон по умолчанию расположен в `templates/corporate_base.pptx`, его описание — в `templates/template_manifest.json`. Другие файлы можно передать явно:

```powershell
.\run.ps1 inspect-template --template templates/corporate_base.pptx --manifest templates/template_manifest.json
.\run.ps1 build examples/presentation.json --output output/demo.pptx --template templates/corporate_base.pptx --manifest templates/template_manifest.json
```

## Подключение внутренней модели

Адаптер ожидает API, совместимый с `chat/completions`. Если внутренний сервис использует другой контракт, потребуется адаптация клиента. Сначала узнайте у владельца сервиса адрес API, имя модели, способ авторизации и поддерживаемый формат ответа.

Если локальной конфигурации ещё нет, создайте её из примера:

```powershell
if (-not (Test-Path -LiteralPath config/llm.local.json)) {
    Copy-Item config/llm.example.json config/llm.local.json
}
```

В `config/llm.local.json` задайте `base_url` и `model`. Например, если сервис публикует `.../v1/chat/completions`, в `base_url` нужен адрес до `/v1` включительно. Секрет храните в переменной окружения, имя которой задано в `api_key_env`:

```powershell
$env:SUPERSLIDE_LLM_API_KEY = '<токен внутреннего API>'
```

Переменная действует для текущего сеанса PowerShell. Файл `.env` автоматически не читается. Адрес и имя модели при необходимости можно переопределить через `SUPERSLIDE_LLM_BASE_URL` и `SUPERSLIDE_LLM_MODEL`. Локальная конфигурация, `.env`, окружение Python и папка `output` исключены из Git.

Если сервис поддерживает запрос списка моделей, узнать доступные имена можно так, подставив его базовый адрес:

```powershell
.\run.ps1 models --base-url 'https://llm.company.example/v1'
```

В проверенной локальной конфигурации используется модель `glm-5.3`. Для другого сервиса выберите точный идентификатор модели из его ответа и настройте авторизацию.

Основные настройки модели:

| Ключ | Назначение |
| --- | --- |
| `response_format` | `json_object` по умолчанию; `json_schema` при поддержке строгой схемы сервисом; `none`, если сервис не принимает этот параметр |
| `max_output_tokens` | Лимит длины ответа |
| `token_limit_parameter` | Имя параметра API: `max_tokens` или `max_completion_tokens` |
| `max_repair_attempts` | Количество дополнительных запросов для исправления невалидного ответа: от 0 до 2 |
| `timeout_seconds` | Тайм-аут обращения к API |
| `temperature`, `reasoning_effort` | Настройки модели; `null` исключает соответствующий параметр из запроса |
| `max_prompt_chars` | Ограничение размера запроса в символах |
| `context_window_tokens` | Необязательный ориентир для предварительной оценки контекста; не заменяет фактический лимит модели |
| `trust_env_proxy` | Использовать прокси из окружения; `false` направляет запрос прямо к API, сохраняя проверку TLS-сертификата |

Проверенный профиль для `glm-5.3`: `reasoning_effort: "low"`, `max_output_tokens: 16000`, `timeout_seconds: 240`, `trust_env_proxy: false`. Прямое подключение к API работает; прокси из окружения мешал корректному TLS-соединению. Проверка TLS-сертификатов остаётся включённой. Если ответ обрывается из-за лимита длины, увеличьте `max_output_tokens` в пределах возможностей модели; для проверенной презентации использован лимит 16 000.

Содержимое документов передаётся на адрес из конфигурации только при явном запуске `draft`. Команда `models` обращается к API за списком моделей и не передаёт документы. До работы с корпоративными документами проверьте адрес сервиса. Повторные попытки исправления JSON также вызывают модель.

## Генерация из запроса и документов

Для первого прогона используйте демонстрационные файлы. `examples/task.txt` задаёт задачу, `examples/source.txt` содержит вымышленные сведения и показатели.

```powershell
.\run.ps1 draft --task-file examples/task.txt --documents examples/source.txt --config config/llm.local.json --output output/glm-draft.json --sources-output output/glm-sources.json
.\run.ps1 validate output/glm-draft.json --sources output/glm-sources.json
.\run.ps1 build output/glm-draft.json --sources output/glm-sources.json --output output/glm-presentation.pptx --report output/glm-presentation.report.json
```

Между генерацией и сборкой можно открыть `output/glm-draft.json` и исправить содержание вручную. Исправленный JSON нужно снова проверить. Для правки отдельного слайда достаточно изменить его поля и повторить сборку. Ссылки `source_refs` сохраняются в заметках слайдов. Текстовая модель выбирает фотографии по `description` и `tags` каталога; байты изображений ей не передаются, мультимодальная модель для этого не нужна. Выбор фотографии и достоверность подписи проверяет пользователь.

Каждый ответ модели проходит пробный рендер без записи файла: если текст не помещается в поле макета даже минимальным кеглем, генератор возвращает модели номер слайда и поля с указанием сократить или суммаризовать текст, сохранив ключевые факты, числа, `source_refs` и число слайдов. На исправление отводится до `max_repair_attempts` повторных запросов; если текст всё ещё не помещается, генерация завершается ошибкой. Для заранее подготовленного JSON без модели такая проверка выполняется при сборке и остаётся ошибкой сборки.

Извлечение документов доступно отдельно и не вызывает модель:

```powershell
.\run.ps1 extract examples/source.txt --output output/sources.json
```

Поддерживаются TXT и MD в UTF-8, текст и таблицы DOCX, PDF с текстовым слоем. По умолчанию допускается до 10 документов, до 25 МиБ на файл, до 100 000 извлечённых символов на файл и до 160 000 суммарно. Превышение лимитов считается ошибкой; документы не обрезаются молча. Извлечение текста не сохраняет сложную вёрстку документа. Сканы PDF без текстового слоя требуют OCR, который в MVP не реализован. Изображения документов не интерпретируются моделью.

## Локальный веб-интерфейс

Тот же конвейер доступен в браузере: задача, документы, структура слайдов, сборка и скачивание — на одном экране. Команда запускает локальный сервер и, с флагом `--open`, сразу открывает интерфейс:

```powershell
.\run.ps1 serve --open
```

Интерфейс публикуется на `http://127.0.0.1:8765` (порт и хост задаётся параметрами `--port` и `--host`; допустимы только `127.0.0.1` и `localhost`). Порядок работы:

1. Кнопка «Подключение» задаёт API-ключ корпоративной модели. Ключ хранится только в памяти процесса и не записывается на диск; остальная конфигурация берётся из файла, указанного в `--config`.
2. Опишите задачу, при необходимости перетащите до 10 документов (PDF, DOCX, TXT, MD; до 25 МиБ на файл и 50 МиБ суммарно) и выберите количество слайдов от 3 до 20. Кнопка «Создать структуру» обращается к настроенной модели.
3. Готовая структура показывается списком слайдов: заголовки, цитаты и варианты оформления можно изменить до сборки. Кнопка «Открыть демопример» загружает демонстрационную структуру без обращения к модели.
4. Для слайдов с фотографиями (фотообложка, «Фото и текст», «Крупное фото», галерея) под списком вариантов появляется лента миниатюр: можно выбрать готовое фото из корпоративного каталога или загрузить своё с компьютера (PNG/JPEG до 15 МиБ; до 10 фото и 100 МиБ за сеанс). Загруженные фото проверяются так же, как каталог, сохраняются в `output/web/images`, участвуют в сборке и предлагаются модели при последующих генерациях этого сеанса. Описание выбранного фото подставляется в `alt_text`; видимый `caption` и уместность фотографии проверяйте вручную. У титульного слайда фото доступно только для варианта «Фотообложка»: выбор фото включает этот вариант, «Без фото» возвращает базовый.
5. Кнопка «Открыть JSON-файл» загружает ранее скачанный `draft.json` обратно в редактор: JSON проверяется и нормализуется тем же контрактом, что и командная `validate`. Так доступен полный цикл «скачал — поправил — загрузил — пересобрал» без командной строки.
6. «Создать PowerPoint» собирает нативный PPTX; доступны для скачивания презентация, проверенный JSON структуры и отчёт сборки.

Задания генерации и сборки выполняются одним фоновым потоком и хранятся в памяти процесса: после перезапуска сервера список заданий очищается. Загруженные документы и результаты сохраняются в `output/web`. Сервер принимает соединения только с локального интерфейса, отклоняет чужие `Host` и `Origin`, требует служебный заголовок для изменяющих запросов и не записывает в журнал имена файлов, тексты заданий и ответы модели.

## Локальные фотографии

Фотобанк описан в `assets/images/catalog.json`. Начальный набор фотографий извлечён из предоставленной корпоративной презентации; для каждой записи сохранены исходный слайд и media-файл. Посмотреть доступные ID и описания можно без обращения к модели:

```powershell
.\run.ps1 assets
.\run.ps1 assets --asset-catalog assets/images/catalog.json
```

Пример записи каталога:

```json
{
  "images": [
    {
      "id": "steel_coils",
      "file": "steel_coils.jpg",
      "description": "Рулоны листовой стали в производственном цехе.",
      "tags": ["сталь", "продукция", "производство"],
      "source_slide": 72,
      "source_media": "ppt/media/image82.jpeg",
      "width": 2499,
      "height": 1666
    }
  ]
}
```

`file` — путь относительно папки выбранного `catalog.json`. Изображение должно находиться внутри этой папки или её подпапок. Поддерживаются PNG и JPEG (`.png`, `.jpg`, `.jpeg`), до 15 МиБ и до 40 миллионов пикселей на файл. Абсолютные пути, `..`, сетевые URL, повторяющиеся ID и повреждённые изображения отклоняются. Файлы проходят проверку до генерации. Для добавления фотографии скопируйте её в папку фотобанка и добавьте уникальный ID, описание и теги в каталог; указанные `width` и `height` должны совпадать с реальным размером.

В JSON презентации используется только `asset_id`, например `steel_coils` или `production_worker`. Пути и URL в слайде не задаются. `fit: "cover"` заполняет рамку с сохранением пропорций и кадрированием краёв; `fit: "contain"` сохраняет изображение целиком внутри рамки. Значение по умолчанию — `cover`. `alt_text` содержит краткое описание изображения, а `caption` — видимую подпись, если она предусмотрена макетом.

Команды `draft`, `validate` и `build` по умолчанию используют проектный каталог `assets/images/catalog.json`. Другой каталог передавайте явно и используйте его на всех этапах:

```powershell
.\run.ps1 draft --task-file examples/task.txt --documents examples/source.txt --config config/llm.local.json --asset-catalog assets/images/catalog.json --output output/draft.json
.\run.ps1 validate output/draft.json --sources output/draft.sources.json --asset-catalog assets/images/catalog.json
.\run.ps1 build output/draft.json --sources output/draft.sources.json --asset-catalog assets/images/catalog.json --output output/draft.pptx
```

При отсутствии фотографий в каталоге модель получает только макеты без изображений. Галерея рассчитана на три разных фотографии; если доступно меньше трёх, модель не должна выбирать этот макет. Модель не создаёт и не скачивает фотографии.

## Формат презентации

Корневой объект содержит `template_version: "1.2"`, `title` и массив `slides`. Версия `"1.0"` по-прежнему принимается для шести исходных типов; все 14 типов доступны начиная с `"1.1"`. Для выбора оформления, отличного от `default`, нужна версия `"1.2"`. Каждый слайд содержит `layout_id`, необязательный `variant_id` со значением `"default"` по умолчанию, массив `source_refs` и необязательные заметки `notes`. Содержимое задаётся обычными строками и данными. HTML не используется как разметка; координаты и оформление определяются шаблоном, а не ответом модели.

| `layout_id` | Поля содержания |
| --- | --- |
| `title_slide` | `title`, `subtitle`, `author`, `date`; `image` обязателен только для варианта `photo` |
| `bullet_list` | `title`, `bullets` |
| `two_columns` | `title`, `left` и `right`; каждая колонка содержит `heading`, `bullets` |
| `quote` | `quote`, `author` |
| `table` | `title`, `columns`, `rows`, `footnote` |
| `bar_chart` | `title`, `categories`, `series`, `unit`, `takeaway`; каждый ряд содержит `name`, `values`, `role` |
| `section_divider` | `number`, `title`, `subtitle` |
| `photo_text` | `title`, `image`, `heading`, `bullets`, `caption` |
| `image_spotlight` | `title`, `image`, `caption` |
| `gallery` | `title`, `images`: ровно три объекта изображения с `asset_id`, `fit`, `alt_text`, `caption` |
| `kpi_cards` | `title`, `cards`: ровно три объекта с `value`, `label`, `detail` |
| `timeline` | `title`, `steps`: ровно четыре объекта с `title`, `text` |
| `comparison` | `title`, `left` и `right`; каждая колонка содержит `heading`, `bullets` |
| `closing` | `title`, `subtitle`, `contact` |

Доступные варианты оформления:

| `layout_id` | Значения `variant_id` |
| --- | --- |
| `title_slide` | `default`, `blue_minimal`, `blue_graphic`, `photo` |
| `bullet_list` | `default`, `accent_panel`, `two_columns` |
| `quote` | `default`, `blue`, `accent` |
| `section_divider` | `default`, `circle_pattern`, `diagonal_pattern` |
| `photo_text` | `default`, `photo_right`, `photo_band` |
| `image_spotlight` | `default`, `white_caption`, `side_panel` |
| `kpi_cards` | `default`, `plain`, `accent_panel` |
| `closing` | `default`, `blue_minimal`, `white_graphic` |
| `two_columns`, `table`, `bar_chart`, `gallery`, `timeline`, `comparison` | `default` |

Один набор содержания можно показать в разных композициях, меняя только `variant_id`. Например, эти слайды имеют одинаковые заголовок и тезисы:

```json
{
  "template_version": "1.2",
  "title": "Сравнение оформления",
  "slides": [
    {
      "layout_id": "bullet_list",
      "variant_id": "default",
      "title": "Направления развития",
      "bullets": ["Качество продукции", "Эффективность процессов"],
      "source_refs": []
    },
    {
      "layout_id": "bullet_list",
      "variant_id": "accent_panel",
      "title": "Направления развития",
      "bullets": ["Качество продукции", "Эффективность процессов"],
      "source_refs": []
    }
  ]
}
```

Набор полей не меняется при переключении оформления, кроме титульного варианта `photo`: ему требуется `image` с `asset_id`, `fit` и `alt_text`. Для остальных титульных вариантов `image` не допускается. Неизвестный вариант или вариант другого типа слайда отклоняется. Модель получает каталог допустимых сочетаний и выбирает оформление по содержанию; фотографические варианты доступны только при наличии подходящих локальных изображений.

В `photo_text` и `image_spotlight` поле `image` — объект с `asset_id`, `fit` и `alt_text`. Например:

```json
{
  "template_version": "1.1",
  "title": "Производство",
  "slides": [
    {
      "layout_id": "photo_text",
      "title": "Развитие производства",
      "image": {
        "asset_id": "steel_coils",
        "fit": "cover",
        "alt_text": "Рулоны листовой стали в цехе"
      },
      "heading": "Направления обсуждения",
      "bullets": ["Качество продукции", "Эффективность процессов"],
      "caption": "Фотография из корпоративного шаблона",
      "source_refs": [],
      "notes": "Демонстрационная структура; фактические результаты не заявлены."
    }
  ]
}
```

В диаграмме роль `company` обозначает компанию и задаёт синий ряд; `comparison` и `neutral` используют дополнительные цвета палитры. Число значений каждого ряда должно совпадать с числом категорий. В таблице число ячеек каждой строки должно совпадать с числом колонок.

Модель ограничена компактными слайдами: до 6 тезисов в `bullet_list`, до 4 тезисов в колонке и в `photo_text`, до 8 строк данных и 5 колонок таблицы, до 8 категорий и 3 рядов диаграммы. Галерея содержит три фотографии, KPI — три карточки, этапы — четыре шага. `kpi_cards.cards[].value` — строка до 20 символов, например `"125 млн ₽"`; её значение должно быть подтверждено источником. Есть также ограничения длины заголовков, подписей и остальных полей. Точные ограничения можно получить из актуальной JSON Schema:

```powershell
.\run.ps1 schema --output schemas/presentation.schema.json
```

`source_refs` содержит идентификаторы фрагментов из файла, созданного командой `extract` или параметром `--sources-output`. При проверке и сборке передавайте этот файл через `--sources`: так проверяется существование указанных идентификаторов. Такая проверка не доказывает, что утверждение действительно следует из источника, — содержание требует проверки человеком. В готовом демонстрационном JSON ссылки пустые, а вымышленные данные обозначены в заметках.

## Изменение фирменных макетов

Связь между логическим `layout_id`, `variant_id`, макетом PowerPoint и `placeholder.idx` описана в manifest. В `layouts[layout_id]` находится композиция `default`; её `variants` содержит самостоятельные описания остальных композиций с собственными полями и координатами. Генератор использует `add_slide(layout)` и заполняет предусмотренные поля. Он не клонирует произвольные слайды из исходной библиотеки.

Для изменения композиции сначала измените генераторный шаблон, затем согласуйте manifest и выполните `inspect-template`. Обычное текстовое поле на слайде исходной презентации не становится автоматически полем генератора. Не следует полагаться только на порядковый номер макета в PowerPoint: после изменения шаблона нужно повторно проверить соответствие полей.

Служебные скрипты запускаются тем же Python с зависимостями. Команда подготовки заново создаёт `templates/corporate_base.pptx` и `templates/template_manifest.json`, заменяя предыдущие версии. Аудит проходит по всем композициям manifest: проверяет пустой шаблон с одним образцом, уникальность 31 физического макета, координаты и типы полей, ссылки на источники оформления, неизменность исходных media и старой фирменной графики, отсутствие внешних зависимостей и OLE, а также создание нативных таблицы, диаграммы и фотографий с повторным открытием PPTX.

```powershell
python scripts/prepare_template.py
python scripts/audit_template.py
```

## Проверка изменений

Проверенная команда запуска автоматических тестов:

```powershell
python -m unittest discover -s tests -v
```

Проверка через приложение требует Windows и **установленного настольного Microsoft PowerPoint**. Скрипт открывает PPTX через COM, экспортирует PDF и PNG всех слайдов и сохраняет отчёт с проверкой высоты текстовых рамок:

```powershell
.\scripts\verify_powerpoint.ps1 -InputFile output/demo.pptx
.\scripts\verify_powerpoint.ps1 -InputFile output/variety.pptx -OutputDirectory output/variety-powerpoint
.\scripts\verify_powerpoint.ps1 -InputFile output/variants.pptx -OutputDirectory output/variants-powerpoint
.\scripts\verify_powerpoint.ps1 -InputFile output/glm-presentation.pptx -OutputDirectory output/glm-powerpoint
```

По умолчанию результаты находятся в `output/powerpoint`: `presentation.pdf`, `slide-01.png` и последующие изображения, `powerpoint-report.json`. Папку можно изменить параметром `-OutputDirectory`; проверка полного набора из 31 варианта сохранена в `output/variants-powerpoint`, 14 прежних композиций — в `output/variety-powerpoint`, а прежней презентации от `glm-5.3` — в `output/glm-powerpoint`. Это проверка конкретных файлов: она не заменяет визуальную проверку таблиц, подписей диаграмм и оформления новых презентаций. Для новых вариантов API проверялся с подменой ответов; успешный прогон через корпоративный сервис относится к прежнему примеру с шестью базовыми типами.

## Границы первой версии

Веб-интерфейс работает только локально, без публикации в сеть; отдельной БД и фоновой очереди нет — задания выполняются в памяти процесса `serve` и очищаются при перезапуске. Не реализованы OCR, извлечение из XLSX, интерпретация изображений документов, произвольная инфографика, think-cell и OLE. Фотографии выбираются из локального каталога по описаниям; генерация изображений и визуальный анализ фотографий моделью не выполняются.

Проверка структуры JSON и PPTX не обнаруживает все визуальные дефекты. После изменения шаблона проверяйте контрольную презентацию в PowerPoint и согласовывайте оформление с владельцем бренда. Скорость генерации и пригодность внутренней модели следует измерять на реальном API и согласованном наборе документов; гарантированное время генерации пока не установлено.
